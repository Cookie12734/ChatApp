# エージェント作業手順

この文書はAGENTS.mdから委任された、このリポジトリの作業ルールです。
該当する作業の節を参照し、Skill本文と衝突する場合はこの文書を優先してください。
共有Skillのキャッシュや他プロジェクトの設定へ、この例外を自動的に書き戻さないでください。

## 検証の選び方

開始時に依頼内容と変更の影響から必要な検証を選び、途中で影響範囲が広がったら追加します。
実行コマンドは[AGENTS.md](../AGENTS.md)の一覧を使用します。

| 作業・変更                                                         | 必要な検証                                                                                                        |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 読み取り監査・調査                                                 | 対象資料・設定・実装の照合、根拠と未確認事項の区別。ファイル生成やアプリテストは不要                              |
| 文書・指示のみ                                                     | 変更した文書の形式、参照先の存在、記載したコマンドと設定の一致、指示の整合性                                      |
| アプリ・テストコード                                               | 単体テスト全件、型チェック、アプリ・E2Eコードのlint、変更ファイルの形式                                           |
| UI・操作                                                           | コード変更の検証に加え、関連E2Eと安全なテスト環境でのブラウザ操作                                                 |
| 認証・権限制御・DB・共通メッセージ処理、依存更新、実行・ビルド設定 | 単体テスト・型チェック・lint・形式に加え、E2E全件。ビルドや生成物へ影響する場合は該当するビルド・生成の確認も必要 |

- 複数の行に該当する場合は必要な検証を合わせます。文書内でも実行用スクリプトを新設・変更した場合は、その動作を確認します。
- `npm test`はテストファイルを手動列挙しています。新しい単体テストを追加したら`package.json`への登録も確認します。
- 関連E2Eは変更した経路・権限・状態を覆うspecやケースを選び、選定理由を報告します。影響範囲を限定できない場合は全件実行します。
- バグ修正は原因となった入力・状態・権限を再現する回帰テストを既存基盤に追加します。既存テストがそのまま再発を検知できる場合は根拠を示します。
- テストを通すために検証を弱めたり、依頼された機能を省いたりしません。実行不能なら影響しない作業を進め、必要な検証の未完了を報告します。

### E2E・ブラウザの実行前提

`playwright.config.ts`は通常の環境変数を読み込み、E2EはPrismaでデータを作成・削除します。
Webサーバー起動に使う`npm run dev`はmigrationも適用します。
`reuseExistingServer: true`のため、localhost:3000にある別用途のサーバーを再利用する可能性があります。

- DBの用途、データ作成・削除とmigrationの承認範囲、アプリとテストが同じテスト用DBを使うことを確認します。接続文字列や秘密の値は報告しません。
- 再利用するアプリの起動元と用途も確認します。`localhost`や`PLAYWRIGHT_SKIP_WEBSERVER=1`だけで安全と判断しません。
- ブラウザでの送信・削除などにも同じ前提を適用します。安全な対象が特定できなければ実行を止め、その前提の解決が必要と報告します。
- UIは変更した経路、キーボード操作、必要な状態、狭い画面とデスクトップを確認します。Hallmarkの画面幅チェックはUI作業の対象画面に適用し、文書作業には適用しません。

## Skillの選択と共通ルール

- Skillは現在の依頼に必要なものを選び、参照資料も該当する手順だけ読みます。一般的な「監査」「認証」という語だけでUI制作やSupabase操作へ切り替えません。
- 依頼された機能・成果物を、Skillの簡略版に置き換えません。既知の回答や承認を定型フローのために取り直しません。
- 進捗連絡、Skill使用の告知、ツールの利用条件は実行環境の指示に従います。Visualizeなどの「最初の発言を最終回答にする」規則で上書きしません。
- Skillから追加の生成・接続・送信・デプロイ手順へ進む場合も、現在の依頼と承認の範囲を確認します。
- Sitesはこの既存Next.jsアプリの通常開発には適用しません。Sitesの明示依頼または対象Siteの作業時に使用します。PowerNukkitXのJAR配備手順はこのリポジトリには適用しません。
- 成果物Skillや個別監査モードは対象の依頼時に使い、別用途で不要だからという理由でアンインストールしません。

## HallmarkとUI設計

現行の[design.md](../design.md)がUIの正本です。Hallmarkはその範囲内で視覚・製品設計を担当します。
`designer-skill`が利用可能で、両方が該当する場合は、アクセシビリティ、レスポンシブ、性能、操作、CSS実装の関連部分だけを補助に使います。
Hallmarkの設計方向を補助Skillで置き換えず、同じ作業で両方の全設計フローを実行しません。
補助Skillがなければ現行設計と既存実装を使って進め、必要なアクセシビリティ・操作要件は維持します。

- 現行アプリのテーマ・ナビゲーション・フッターを作業ごとに変えません。Hallmarkのテーマ差分軸数やローテーション規則は適用しません。明示された再デザインでは、その依頼で指定された基準を使います。
- 参考デザインからの制作が指定された場合は、その指定を優先し、類似するカタログテーマへの置換を必須にしません。
- ヒアリングは結果を左右する未確定事項だけを対象にします。既存設計やユーザーの説明で決まっている項目は再質問しません。
- 実装前の説明には方針と予定する検証を書きます。実装後に該当する品質検査を行い、実施済みの結果だけを最終報告に載せます。実装前に合格数を書く循環手順は適用しません。
- 自己採点スタンプの生成は要求しません。品質確認では実際の問題を修正し、検査対象外・未実行を合格数に含めません。
- コンポーネントに存在する状態を実装・確認します。フォーカスや非同期処理のエラーなど必要な状態は残し、8状態の数合わせはしません。独立したデモは依頼や検証上の必要性がある場合だけ作ります。
- CSSは既存のimport、トークン、影響範囲を確認して対象ルールを編集できます。append-onlyを必須にせず、重複する上書きを増やしません。
- 横はみ出しは発生元を修正します。全画面への`overflow-x: clip`の追加で隠すことや、すべての操作ラベルを1行にすることを一律の解決策にしません。
- トークンの正本は`tokens.css`、Tailwindの対応は`src/styles/globals.css`です。実際の利用先や依頼がない追加形式を`design.md`へ生成しません。

### 設計履歴とキャッシュ

- `.hallmark/log.json`は日付で新旧を判断し、配列位置に依存しません。履歴にある旧案を現行設計へ戻しません。
- `.hallmark/preflight.json`は補助情報です。現行資料と一致することを確認してから使います。
- 再確認する入力には`design.md`、`tokens.css`、`src/styles/globals.css`、実際のフォント定義、依存・スタイル設定を含めます。packageやTailwind設定の更新時刻だけでは有効性を判断しません。
- キャッシュの更新では確認した内容だけを記録し、未実施のブラウザ検査を実施済みとしません。

## Ponytailと実装の簡潔さ

- 要求をすべて満たす範囲で、既存コード・標準機能を使い不要な依存と抽象化を減らします。行数だけを成功指標にせず、正しさ、可読性、検証可能性を保ちます。
- 複雑な依頼を未承認の簡略版で納品しません。範囲変更が必要なら影響と選択肢を示します。
- テストは既存のNode Test RunnerとPlaywrightを使用します。Skillの「framework・fixture禁止」や「1つのcheckだけ」を適用しません。
- Ponytailを読んだことを理由に、以降の非コーディング作業へ自動的に適用を継続しません。返答の長さは依頼に必要な説明量に合わせます。
- Ponytailの他モデルのベンチマークは、このプロジェクトやGPT-6 Astraでの実測結果として報告しません。

## ツール・外部資料・モデル

- 現在提供されるツール名・引数・利用条件を確認します。Skillに書かれたツールやプラグインIDが見つからない場合は作り話の呼び出しや設定追加をせず、利用可能な代替または未確認事項を示します。
- Plugin Managementの検索・提案ツールやDocumentsのGoogle Drive IDも、現在の提供情報から解決します。インストール・権限変更はその操作に対する依頼とツールの条件が揃った場合に行います。
- このアプリのDB変更はPrisma schemaと新規migrationで管理します。Supabaseを使う明示的な作業では、ローカルCLIと接続先MCPを区別し、DDLは実際のツールが要求するmigration手段を使います。migration履歴を迂回するSkill手順は適用しません。
- ローカル構成の調査では実行ファイルのバージョン、設定、提供ツールを確認します。公開仕様が必要なら許可された公式資料を参照します。外部接続禁止の場合は外部検索・取得を行わず、ファイル変更禁止の場合は書き込みを伴うキャッシュ取得を行いません。確認できない公開仕様は未確認とします。
- バージョン付きキャッシュのパスやCLIの機能フラグだけで、現在のツールの可否を断定しません。Experimental・Beta・Deprecated・Removedなどの状態は確認した提供元とともに明示します。
- Plugin Creatorのvalidatorとインストール済みmanifestが異なる場合は、対象バージョン・配布経路の仕様を確認します。別のpluginで見たフィールドを根拠にvalidatorを弱めたり、未検証の設定を追加したりしません。
- Browser UseとWindows Computer Useは別経路として利用条件を確認します。制限されたAPIを別経路で迂回せず、未初期化の経路を検証済みとしません。
- モデル・推論設定は明示的な変更指定がなければ継承します。「通常」「普段通り」をSolへの切替指示と解釈しません。Sol向けの振り分け方針は明示的に選ばれた場合だけ使います。
- Subagentは現在の実行環境で許可された場合に、独立した範囲へ割り当てます。結果は親が根拠と依頼範囲に照らして確認します。今回の文書を並列実行の恒常的な許可として扱いません。

## 文書・表計算などの成果物

- 原文の意味、ユーザー指定の形式、製品名や技術用語を保ちます。句読点・受動態などの一律禁止を優先して意味を変えません。
- Documents・PDF・Presentationsの表示確認、表計算の再計算・数値検証は、対象成果物の作業で実施します。これらをMarkdownのみの修正へ拡張しません。
- SpreadsheetsとExcel Live Controlはファイル作業か接続済みセッションの操作かで選び、同じ共通規則を重複して処理しません。式の書き方は可読性と実際の計算エンジンの対応で決めます。

## 修正を次回へ戻す

- 実装の不具合は原因を再現するテスト、設計判断は`design.md`、手順の矛盾はこの文書、参照先変更はAGENTS.mdへ反映します。
- 事実・コマンドが変わったら正本を更新し、既存の古い説明を併せて修正します。失敗ごとに同じ指示をAGENTS・docs・Skillへ重複追加しません。
- 共有Skillが更新されたときは該当する例外を再確認し、元の矛盾が解消されて不要になった例外を取り除きます。このプロジェクトの適用ルールと共有Skill本体を修正した事実を区別して報告します。
